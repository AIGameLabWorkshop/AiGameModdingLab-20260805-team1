# Specs/Assumptions

このフォルダには、子供たちが書いた仕様書（`Specs/TEMPLATE.md`）を実装する際に、AIエージェント（**BrickBreaker 仕様実装エージェント**）が発見した「曖昧な点」や「補完した判断」を記録したドキュメントが保存されます。

## 目的

仕様書を実装に落とし込む過程で、以下のような問題が発生することがあります：

- **曖昧な表現** - 「大きくなる」ってどのくらい？
- **実装方法が複数** - パーティクルはどんな形？何個？
- **エッジケースが不明** - 複数回トリガーされたら？
- **技術的な制約** - ゲームの仕組み上、こうする必要がある

このドキュメントは、そうした「判断ポイント」を記録することで：

✅ **仕様書の質を向上させる**  
→ 「良い仕様書とは何か」を子供たちが学べます

✅ **実装との齟齬を防ぐ**  
→ 期待と実際の動作を一致させます

✅ **教育効果を高める**  
→ プロダクト開発の実務を体験できます

## ドキュメント構成

各仕様書に対応した Assumptions ドキュメント（例：`01_simple_powerup.md`）には、以下の内容が記載されます：

### 1. 元の仕様書
実装されたオリジナルの仕様書（TRIGGER/ACTION/TEST）を記録

### 2. 曖昧だった点
仕様書のどの部分が不明瞭だったか

**例：**
- 「パドルが大きくなる」→ どのくらい？（1.5倍と判断）
- 「爆発する」→ 何個のパーティクル？（100個と判断）

### 3. 作られた仮定
曖昧さを補完するために、AIエージェントが作った仮定

**例：**
- パドルは1.5倍のサイズに拡大、3秒後に元に戻る
- パーティクルは虹色で、ボール衝突地点から放射状に飛ぶ

### 4. 判断の理由
その仮定を選んだ理由

**例：**
- 既存コードのパワーアップシステムを参考にした
- ワークショップの子供が理解・カスタマイズしやすい難易度を選んだ

### 5. 実装ノート
実装時に発見したことや、追加実装した内容

**例：**
- どのファイルを修正したか
- 新たに追加したゲーム機能
- 既存機能との相互作用

## 活用方法

### 子供向け
1. 自分の仕様書がどう実装されたかを確認
2. 「曖昧だった点」を見直して、次の仕様書をより正確に書く
3. AIがどう補完したかを参考にして、仕様書を改善

### 講師向け
1. 仕様書の問題点を特定して、フィードバックを準備
2. 同じ間違いがどの子供にも見られるなら、グループ指導の対象に
3. ワークショップの実施後に、学習成果を評価する材料に

## 見本

仕様書サンプル（`Specs/Samples/`）を実装したときの Assumptions ドキュメントが参考になります。
